COVOITURAGE PROJECT GUIDE
========================

1. WHAT THIS PROJECT DOES
-------------------------

This is a backend REST API for a carpooling application. It lets clients:

- Register drivers and passengers.
- Add vehicles for drivers.
- Publish trips made up of ordered stops.
- Search for a trip between any two stops on its route.
- Book seats for a part of a trip.
- Calculate a fare from the selected boarding and drop-off stops.
- Cancel reservations and trips, and complete trips.

The application does not include a website or mobile application. A client
such as Postman sends HTTP requests to the API and receives JSON responses.


2. HOW A REQUEST IS PROCESSED
-----------------------------

The project is organized in layers:

1. Controller
   Receives an HTTP request, reads its path, query parameters, and JSON body,
   and returns an HTTP response. Controllers are in:
   src/main/java/com/youcode/covoiturage/controller

2. Service
   Applies the business rules, such as ownership checks, available-seat checks,
   fare calculation, and trip status changes. Services are in:
   src/main/java/com/youcode/covoiturage/service

3. Repository
   Reads and writes database records using Spring Data JPA. Repositories are in:
   src/main/java/com/youcode/covoiturage/repository

4. Entity
   Describes database data and relationships. Entities are in:
   src/main/java/com/youcode/covoiturage/entity

5. Mapper and DTO
   DTOs are the request and response objects used by the API. MapStruct mappers
   convert between DTOs and database entities.

For example, creating a trip follows this path:
POST /api/trips -> TripController -> TripService -> repositories/database
-> TripResponseDTO -> JSON response.


3. DATA MODEL
-------------

User is a shared Java parent class for Driver and Passenger. It is a JPA
MappedSuperclass, so it does not have its own database table.

- Driver: first name, last name, email, phone, and license number.
- Passenger: first name, last name, email, and phone.
- Vehicle: brand, model, license plate, color, passenger capacity, and owner.
- Trip: driver, vehicle, offered seats, route endpoints, departure time, and
  status.
- StopPoint: a city on a trip, its order, passing time, and cumulative price.
- Reservation: passenger, trip, boarding city, drop-off city, seats, fare,
  booking time, and status.

Main relationships:

- One driver can own many vehicles.
- One driver can publish many trips.
- Each trip uses one vehicle.
- Each trip contains two or more stop points.
- A passenger can make reservations on different trips.
- A trip can have many reservations.

Stop points are stored in their own table, but there is no separate StopPoint
controller. Clients create and update stops as part of a trip request.


4. TRIP ROUTES AND SEGMENT PRICING
----------------------------------

A trip route is an ordered list of stops. Each stop has:

- city
- passingTime
- priceFromDeparture

priceFromDeparture is the cumulative price from the first stop. It is not the
price from the previous stop.

Example:

  Rabat       price 0
  Casablanca  price 40
  Settat      price 70
  Marrakech   price 120

For one seat:

- Rabat to Casablanca costs 40.
- Casablanca to Marrakech costs 120 - 40 = 80.
- Rabat to Marrakech costs 120 - 0 = 120.

The reservation fare is:

  (drop-off cumulative price - boarding cumulative price) * number of seats

The final amount is rounded to two decimal places. For example, two seats from
Casablanca to Marrakech cost 80 * 2 = 160.00.


5. TRIP RULES AND STATUSES
--------------------------

Trip statuses are:

- PUBLISHED: the trip can be searched and booked.
- FULL: all offered seats have confirmed reservations.
- COMPLETED: the driver marked the trip as completed after departure.
- CANCELLED: the driver cancelled the trip.

Creating or updating a trip checks:

- The driver exists.
- The vehicle exists and belongs to that driver.
- The offered seat count is at least 1 and no greater than the vehicle's
  passenger capacity.
- There are at least two stops.
- Stop cities are not repeated (comparison ignores letter case).
- The first stop is in the future.
- Each stop time is later than the previous stop time.
- The first stop price is 0.
- Each later cumulative price is greater than the previous price.

The first stop becomes the trip's departure city and departure date. The last
stop becomes its arrival city. Stop order is assigned by the order of the list.
A newly created trip starts as PUBLISHED.

Trip search:

- Matches the requested departure and arrival cities as stops on the same trip.
- Requires the departure stop to come before the arrival stop.
- Returns only PUBLISHED trips that still have seats.
- Can optionally filter by departure date and maximum price for that segment.
- Sorts by departure time and limits page size to 50.
- Calculates segment price by subtracting the two stops' cumulative prices.

Completing a trip:

- Requires the supplied driver ID to be the trip owner.
- Is rejected if the trip is already COMPLETED or CANCELLED.
- Is rejected if the departure time is still in the future.

Cancelling a trip:

- Requires the supplied driver ID to be the trip owner.
- Is rejected if the trip is already COMPLETED or CANCELLED.
- Cancels all of the trip's CONFIRMED reservations, then marks the trip
  CANCELLED.

Deleting a trip also checks the driver owner, but the service does not provide
a special rule for trips that already have reservations. Database relationships
may prevent deleting a trip with related data.


6. RESERVATION RULES AND FARE
-----------------------------

Creating a reservation checks:

- The passenger and trip exist.
- The trip is PUBLISHED.
- Boarding and drop-off cities are stops on that trip.
- Boarding comes before drop-off.
- Enough seats remain.
- The same passenger does not already have a CONFIRMED reservation on that trip.

The API calculates the saved fare itself. It also sets the booking time to the
current time and the status to CONFIRMED. The request DTO currently requires
totalAmount, reservationDate, and status fields for input validation, but the
create service does not use those supplied values to determine the saved fare,
date, or status.

Available seats are calculated by adding the seats from all CONFIRMED
reservations on the trip and subtracting that total from offeredSeats. This is
a trip-wide seat count, not a separate seat count for each overlapping route
segment.

If a booking uses all offered seats, the trip changes from PUBLISHED to FULL.
Cancelling a reservation:

- Requires the supplied passenger ID to own the reservation.
- Is rejected if it is already CANCELLED.
- Must happen at least 24 hours before the trip's departure.
- Changes the reservation status to CANCELLED.
- Changes a FULL trip back to PUBLISHED if seats become available.

Updating a reservation checks the owner and maps the supplied request fields
onto the existing reservation. Unlike creation, this update path does not
recalculate the fare or repeat the trip/stop/seat booking checks.

GET /api/reservations returns all reservations. There is no GET-by-ID route.
A passenger can also view their own reservation history through the
PassengerController.


7. DRIVERS, PASSENGERS, AND VEHICLES
------------------------------------

Drivers:

- Email and license number must be unique among drivers.
- Drivers can be listed, searched by name/email, and fetched by ID.
- Update and delete HTTP routes require driverId and check it matches the
  driver being changed.

Passengers:

- Email must be unique among passengers.
- Passengers can be listed, searched by email, and fetched by ID.
- Reservation history is sorted newest first.
- Update, delete, and reservation-history routes check that the supplied
  passenger ID matches the passenger being accessed.

Vehicles:

- Each vehicle belongs to a driver.
- The vehicle request's driverId must match the driver ID in the URL.
- Passenger capacity must be between 1 and 8.
- License plates must be unique.
- Read, update, and delete operations check that the vehicle belongs to the
  driver in the URL.
- A vehicle linked to a trip cannot be deleted; the API returns a conflict.


8. HTTP ENDPOINTS
-----------------

Base URL when using the supplied Docker Compose setup:
http://localhost:8081

DRIVERS - /api/drivers

  POST   /api/drivers
         Create a driver.

  GET    /api/drivers
         List drivers.

  GET    /api/drivers/{id}
         Get one driver.

  GET    /api/drivers/search?query=Hamid
         Search driver names and emails.

  PUT    /api/drivers/{id}?driverId={driverId}
         Update the driver's profile.

  DELETE /api/drivers/{id}?driverId={driverId}
         Delete the driver.

PASSENGERS - /api/passengers

  POST   /api/passengers
         Create a passenger.

  GET    /api/passengers
         List passengers.

  GET    /api/passengers/{id}
         Get one passenger.

  GET    /api/passengers/search?email=sara@example.com
         Find a passenger by email.

  GET    /api/passengers/{id}/reservations?requestingPassengerId={passengerId}
         Get that passenger's reservation history.

  PUT    /api/passengers/{id}?passengerId={passengerId}
         Update the passenger's profile.

  DELETE /api/passengers/{id}?passengerId={passengerId}
         Delete the passenger.

VEHICLES - /api/drivers/{driverId}/vehicles

  POST   /api/drivers/{driverId}/vehicles
         Create a vehicle for the driver.

  GET    /api/drivers/{driverId}/vehicles
         List the driver's vehicles.

  GET    /api/drivers/{driverId}/vehicles/{id}
         Get one vehicle owned by that driver.

  PUT    /api/drivers/{driverId}/vehicles/{id}
         Update the vehicle.

  DELETE /api/drivers/{driverId}/vehicles/{id}
         Delete the vehicle if no trip uses it.

TRIPS - /api/trips

  POST   /api/trips
         Publish a trip with its ordered stops.

  GET    /api/trips/search?departureCity=Rabat&arrivalCity=Marrakech
         Search for an available segment. Optional query parameters:
         date (YYYY-MM-DD), maxPrice, page, and size.

  GET    /api/trips/{id}
         Get trip, driver, vehicle, stops, status, and remaining seats.

  PUT    /api/trips/{id}?driverId={driverId}
         Update the driver's trip and route.

  DELETE /api/trips/{id}?driverId={driverId}
         Delete the trip.

  PATCH  /api/trips/{id}/cancel?driverId={driverId}
         Cancel a trip and its confirmed reservations.

  PATCH  /api/trips/{id}/complete?driverId={driverId}
         Mark a departed trip complete.

RESERVATIONS - /api/reservations

  GET    /api/reservations
         List all reservations.

  POST   /api/reservations
         Book seats for a passenger on a trip segment.

  PUT    /api/reservations/{id}?passengerId={passengerId}
         Update a reservation owned by the passenger.

  PATCH  /api/reservations/{id}/cancel?passengerId={passengerId}
         Cancel a reservation, subject to the 24-hour rule.

  DELETE /api/reservations/{id}?passengerId={passengerId}
         Delete a reservation owned by the passenger.


9. OWNERSHIP CHECKS AND SECURITY LIMITATION
-------------------------------------------

Some routes ask for driverId or passengerId and compare it with the owner stored
on the requested record. This prevents accidental use of the wrong ID in normal
API examples.

There is no login, password, token, or Spring Security authentication in this
project. The client supplies those IDs in the URL, so a real user could claim
another person's ID. These ownership checks are not a replacement for
authentication and authorization in a production application.


10. ERRORS
----------

Errors use a standard ProblemDetail JSON response with fields such as title,
detail, instance, timestamp, and an error type/code.

Common HTTP responses:

- 400 Bad Request: invalid input or business rule, such as invalid stops,
  invalid seat count, or searching the same city.
- 403 Forbidden: the supplied driver/passenger ID is not the record owner.
- 404 Not Found: the requested driver, passenger, vehicle, trip, or
  reservation does not exist.
- 409 Conflict: duplicate email/license/plate, duplicate booking, a final
  status, full trip, or vehicle still in use.
- 500 Internal Server Error: unexpected errors not handled as a business error.

Bean Validation checks request fields such as required names, valid email,
positive seat counts, and required trip stops before controller methods run.


11. SAMPLE DEVELOPMENT DATA
---------------------------

When the dev profile is active, app.seed.enabled=true causes demo data to be
created at application startup. The seed code adds missing records rather than
recreating its known seed records on every restart.

The seeded demo contains at least five drivers, passengers, vehicles, trips,
and reservations, plus route stop points. It includes:

- Hamid El Amrani as a driver.
- A Dacia Logan owned by Hamid.
- Hamid's Rabat -> Casablanca -> Settat -> Marrakech trip.
- Sara's confirmed booking from Rabat to Casablanca.
- That segment costs 40.00 for one seat.

The seed date is calculated relative to the day the app starts. The API port
used by Docker Compose is 8081 on the host. The Postman collection is:
postman/Covoiturage.postman_collection.json

The collection uses direct URLs and fixed sample IDs. Its create/update/delete
requests assume a clean database with the five seed records already present.


12. RUNNING THE APPLICATION AND TESTS
-------------------------------------

Recommended Docker startup:

  cp .env.example .env
  docker compose up -d --build

View application logs:

  docker compose logs -f app

Run only the database and start the application locally:

  cp .env.example .env
  docker compose up -d db
  DB_PORT=5433 SPRING_PROFILES_ACTIVE=dev ./mvnw spring-boot:run

The local command connects to the database through host port 5433 and enables
the dev profile (which turns on seed data). When running directly with Maven,
the API is at http://localhost:8080. Docker Compose maps it to port 8081.

Run automated tests:

  ./mvnw test

Tests use an in-memory H2 database in PostgreSQL compatibility mode, so the
automated test suite does not need a running PostgreSQL server.

To completely reset the Docker database volume:

  docker compose down -v

This deletes the local PostgreSQL data. Starting the app again with the dev
profile runs the seed on the fresh database.


13. IMPORTANT PROJECT LIMITS
----------------------------

- There is no authentication or user login.
- There is no separate StopPoint API; stops are managed through Trip requests.
- There is no GET-by-ID reservation endpoint; GET /api/reservations lists all
  reservations.
- Reservation updates do not perform the same fare and availability
  calculations as reservation creation.
- Available seats are counted for the whole trip, not independently for every
  overlapping segment.
- The API does not explicitly reject past trips during search; search filters
  by trip status and seats, and the optional date filter is chosen by the
  client.
